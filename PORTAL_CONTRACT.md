# Northstar portal contract

Tenant configuration may optionally include `contactPhone`, `contactEmail`, and `serviceArea`. These fields are sanitized and exposed only through the public tenant manifest so attached landing pages can render consistent call-to-action and service-area copy without hard-coding business identity.

Northstar is the owner-facing portal attached to service-business landing pages. Landing pages may link owners to `/portal?service=plumbing` during the demo phase; the local server aliases `/portal` to the owner portal entry page. Production must resolve the tenant from the authenticated session on the server.

Deployments may extend the built-in service tenants with `NORTHSTAR_TENANTS_JSON` (an array of `{ slug, businessName, serviceLabel, timeZone, accent?, accentSoft?, focus?, intakeFields? }`); `leadStages` accepts 2–12 bounded stage labels. The default pipeline is `New`, `Contacted`, `Qualified`, `Estimate sent`, `Won`, and `Lost`; `Converted` remains reserved for scheduled work.. Each optional `intakeFields` entry is `{ id, type, label, required?, options? }`; IDs, field types, labels, option counts, and value lengths are bounded and sanitized before the fields reach a public manifest. Map landing-page service keys with `NORTHSTAR_SERVICE_TENANTS_JSON` (an object of service key to tenant slug). `NORTHSTAR_CATALOG_JSON` may provide up to 500 tenant-bound customer-safe pricebook items `{ tenantId, id?, name, description, priceFrom, category?, durationMinutes?, taxable?, checklist? }`; invalid entries are ignored, configured items are read-only deployment defaults, and owner-created items remain persisted and editable through the authenticated catalog route. Optional brand colors must be six-digit hex values and focus copy is bounded; sanitized values are returned by the public tenant manifest for owner-portal presentation. `NORTHSTAR_OWNERS_JSON` may provide an array of tenant-bound owner records `{ id, name, email, passwordDigest, tenantId }` so each attached landing-page business can have its own owner login. Invalid entries are ignored; configured staff and owner accounts remain tenant-bound.

## Current demo seam

When a configured tenant sets `autoAssignOnlineBookings: true` in `NORTHSTAR_TENANTS_JSON`, normalized online bookings are assigned to the highest-scoring available qualified technician during persistence, confirmed, and notified. If no safe match exists, the booking remains unassigned for dispatch review.

- `tenant-config.js` contains presentation-only configurations for plumbing, power washing, electrical, mobile car wash, and a home-services default.
- `app.js` applies the selected tenant name, service label, accent, and dashboard focus line.
- The owner sign-in dialog is intentionally a demo boundary. It does not collect, transmit, or validate credentials.
- HTTP deployments fail closed when the authenticated API session cannot be established; static preview data is available only when the portal is opened explicitly from `file:`
- API and static responses set CSP, clickjacking, MIME-sniffing, referrer, and permissions policies; `NODE_ENV=production` also enables HSTS
- `server.mjs` provides a dependency-free local API with signed demo sessions, tenant-scoped record routes, and restart-safe development persistence.

## Production boundary

1. Landing page: lead capture and owner-login link, with no direct access to another tenant's data.
2. Identity service: authenticate the owner and return a short-lived session with `ownerId` and `tenantId`.
3. Portal API: authorize every query and mutation against the session's `tenantId`; never use a query-string tenant as an authorization decision.
4. Northstar UI: consume a tenant-scoped API and render the appropriate service vocabulary, workflows, and metrics.

## Recommended API shape

- `POST /api/public/leads` → accept a constrained landing-page inquiry using a service key; validates email/phone shape, preserves submitted contact fields, records a system-attributed `lead.received` audit event, preserves bounded campaign attribution fields when supplied, and supports an `Idempotency-Key` header to make retries safe; identical retries return the original lead, while a different payload under the same key returns `409 idempotency_key_reused`; production must add stronger abuse controls and durable storage
- Public landing-page and signed-portal mutation routes apply bounded per-client/per-service throttling and return `429 rate_limited` with `Retry-After`; configure `NORTHSTAR_PUBLIC_LEAD_RATE_LIMIT` and `NORTHSTAR_PUBLIC_MUTATION_RATE_LIMIT` (1–1000 per minute) for deployment-specific traffic, and invalid production values fail readiness. The limiter uses the direct socket address by default; set `NORTHSTAR_TRUST_PROXY=true` only behind a trusted proxy that overwrites `X-Forwarded-For`, enabling visitor-level limits without trusting that header by default.
- `GET /api/public/availability?service=...&days=...&catalogItemId=...` and `POST /api/public/bookings?service=...` → expose up to 14 days of weekday capacity (with legacy relative labels still supported), date-specific slot IDs, and UTC appointment timestamps in the tenant IANA timezone; an optional tenant pricebook item applies its configured duration to the slot and booking, while active jobs and configured aggregate daily capacity targets remove unavailable slots before booking creates an idempotent tenant-routed customer/job booking, returns both status and customer-portal access tokens, and records a system-attributed `booking.received` audit event
- The public tenant manifest exposes up to eight sanitized `tenant.intakeFields` (`text`, `textarea`, `select`, or `checkbox`) so each attached landing page can render service-specific guided questions without forking the booking client; required fields and select options are enforced server-side, unknown or oversized answers are rejected, and accepted answers are stored on the resulting job or lead under `intakeAnswers` for owner/dispatcher triage
- `GET /api/public/catalog?service=...` → expose the tenant's customer-safe pricebook vocabulary, including service names, starting prices, categories, durations, and taxable flags, so attached landing pages can offer service-specific booking without duplicating tenant configuration
- Configured tenants may replace the default slot preset with validated booking start/end hours, slot intervals, operating weekdays, and blackout dates; those settings are reflected in the public integration manifest
- Repeat bookings from the same tenant customer contact reuse the existing customer record while creating a new job, preserving service history across landing-page visits
- `GET /api/public/tenant?service=...` → return safe tenant branding plus canonical booking, owner-portal, and owner-authentication paths for a service landing page; it never exposes owner or customer data, and the owner path remains subject to authenticated session access
- The owner portal presentation resolver hydrates its safe branding from `/api/public/tenant`, so environment-configured service tenants render their own business name and service label without exposing tenant data to public customer pages
- `booking.html?service=...` → reusable browser form for the public availability/booking contract, returning a customer status link after booking
- `GET /api/public/job-status?token=...` → minimal customer-safe status response for the landing-page handoff, including optional stable slot, normalized appointment fields, multi-visit progress, per-visit statuses, and available reschedule slots
- `POST /api/public/technician-job/location?token=...` → technician-token-only location heartbeat while En route or In progress; coordinates are validated, timestamped, audit-recorded, and never returned through customer-safe portal projections, which expose only live tracking metadata. An `Idempotency-Key` binds each heartbeat payload so mobile replays return a duplicate without another audit event and changed coordinates under the same key return `409 idempotency_key_reused`. The technician workspace offers explicit opt-in live sharing, refreshes no more than once per minute, pauses while the page is hidden, and stops when the job is no longer active. A heartbeat is considered live only for an active job and only for 15 minutes after its recorded timestamp.
- `GET /api/public/job-status/calendar?token=...` → job-status-token-only iCalendar download for the linked appointment; exports only normalized service, time, status, and address
- `POST /api/public/job-status/reschedule?token=...` → apply a new available slot using the status token returned by a landing-page booking; active and no-show jobs can recover to `Confirmed`/`Unassigned`, and the change is conflict-checked, idempotent, and records customer timeline/audit and notification events
- `POST /api/public/job-status/cancel?token=...` → cancel the token-scoped appointment with a required reason, idempotent retry behavior, customer audit/timeline attribution, and the same owner notification surface used by customer-portal cancellation; any active child visits are canceled with the parent so visit progress remains terminal and truthful
- `POST /api/public/customer-portal/request?token=...` accepts an optional `Idempotency-Key`, returns `duplicate: true` for safe retries of the same customer request, and records an actor-attributed `customer.request.received` audit event
- `POST /api/public/customer-portal/location?token=...` → customer-token-only update of the primary service address or addition of a secondary address, with bounded validation, idempotent replay, tenant-scoped persistence, and customer-attributed audit history
- Public status and customer-portal appointment records include optional `enRouteAt` without exposing owner or tenant identifiers
- Malformed JSON and request bodies above 64 KiB return controlled `400 bad_request` responses
- Every response includes an `x-request-id` correlation header; a valid caller-supplied ID (`8–80` ASCII letters, numbers, `:`, `_`, or `-`) is preserved, otherwise Northstar generates one. Error JSON includes the same ID so landing-page agents can report a safe support reference without exposing credentials or payloads.
- Public lead CORS is opt-in through `NORTHSTAR_ALLOWED_ORIGINS`; unlisted origins are rejected during preflight
- API CORS preflight (`OPTIONS /api/...`) returns the allow-list methods and headers only for an origin in `NORTHSTAR_ALLOWED_ORIGINS`; unlisted origins receive `403 origin_not_allowed`, and the allow-list is never inferred from the request
- `GET /api/session` → `{ owner, tenant, permissions }`
- `GET /api/search?q=...&page=...&pageSize=...` → owner/dispatcher/accountant-only tenant-scoped global search across customers, leads, jobs, estimates, invoices, assets, service plans, materials, and purchase orders; owner/dispatcher results also include bounded customer requests, messages, and calls, while results remain role-safe. `page` defaults to 1 and `pageSize` to 20; page size is bounded to 1–50, and the response includes `pagination: { page, pageSize, hasMore, nextPage }` while preserving the existing `results` groups for compatibility.
- Authenticated collection reads such as `GET /api/customers?page=2&pageSize=50` preserve the `items` field and also return `total`, `page`, `pageSize`, and `hasMore`; page size is bounded to 1–200 so large tenants do not require unbounded response payloads
- `POST /api/auth/refresh` → rotate a still-valid owner/staff bearer session, revoke the prior token and session ID, and return a replacement with `expiresAt`; expired or logged-out sessions cannot be refreshed
- `POST /api/auth/login` accepts configured owner or tenant-bound staff credentials without returning or storing passwords; failed attempts are rate-limited and successful sessions use the same signed tenant-scoped token contract. Set `NORTHSTAR_OWNER_EMAIL`, `NORTHSTAR_OWNER_PASSWORD_DIGEST`, `NORTHSTAR_OWNER_TENANT_ID`, optional `NORTHSTAR_OWNERS_JSON`, optional `NORTHSTAR_STAFF_JSON`, and a strong `NORTHSTAR_SESSION_SECRET`; configured owner credentials cannot select a different tenant through the service parameter. The browser adapter single-flights one refresh after a `401` and retries the original request with the rotated token.
- `POST /api/auth/oidc` exchanges a signed OIDC ID token for the same Northstar session contract; when enabled, the server requires HTTPS issuer/JWKS URLs, exact issuer and audience validation, RS256 signature verification with a five-minute JWKS cache, expiration validation, and an explicit `NORTHSTAR_OIDC_ACCOUNTS_JSON` subject-to-tenant/role allowlist. Token tenant and role claims are never trusted for authorization, and malformed OIDC configuration fails production readiness.
- Public intake and customer-token mutation rate-limit buckets are pruned and capped at 5,000 entries, preventing rotating identities or source addresses from causing unbounded in-memory growth; landing-page leads and bookings allow 20 requests per minute per source, while customer/status/estimate/invoice mutations allow 60 requests per minute per source.
- `POST /api/auth/demo-login` is disabled automatically when `NODE_ENV=production`; set `NORTHSTAR_ALLOW_DEMO_LOGIN=true` only for an explicitly isolated preview or smoke environment.
- When demo login is disabled, authenticated record projections contain only persisted tenant records; presentation-only seeded customers, leads, estimates, invoices, plans, activities, and dispatch jobs are omitted.
- When demo login is disabled, the team projection omits the preview technician roster and includes only persisted team members plus configured or runtime technician accounts.
- When demo login is disabled, public catalog responses contain only configured and persisted tenant pricebook entries; preview service names and prices are not advertised to customers.
- `GET /api/ready` returns `200` only when production tenant/service/catalog/account configuration parses and passes shape validation, signing and all webhook secrets are at least 32 characters, owner/staff authentication uses a valid salted scrypt digest or legacy 64-character HMAC digest (or an explicitly provisioned OIDC owner is available), and a writable persistent-state file, SQLite file, or parent directory is present; when `NORTHSTAR_REQUIRE_LIVE_PROVIDERS=true`, it also requires configured lead, inventory, accounting, message, and payment provider URLs, and all provider retry limits must be integers from 0–5. It is the container readiness contract, while `GET /api/health` remains a liveness check.
- `GET /api/openapi.yaml` returns the repository's public OpenAPI 3.0.3 landing-page contract with `application/yaml` content type and no authentication requirement; attached service sites and future agents may retrieve this canonical version instead of copying endpoint assumptions.
- `GET /api/export?type=tenant-snapshot` → owner-only JSON migration/backup snapshot for the authenticated tenant, including schema version, safe tenant metadata, CRM collections, and counts; credentials, secrets, tokens, password digests, idempotency material, and provider authorization fields are stripped before export. Other export types remain CSV and follow their existing role permissions.
- `POST /api/import/tenant-snapshot/validate` → owner-only, non-mutating validation of a proposed schema-version-1 tenant snapshot; requires a matching tenant slug, known collection names, array-shaped collections within bounded limits, and tenant-consistent records, and returns normalized errors/counts without writing live state.
- `POST /api/import/tenant-snapshot` → owner-only application of a validated schema-version-1 snapshot; supplied collections replace tenant data while omitted collections are preserved, imported sensitive control fields are stripped, tenant IDs are normalized server-side, and an `Idempotency-Key` makes migration retries safe.
- Set `NORTHSTAR_BACKUP_FILE` to an optional separate writable path to retain the previous valid JSON snapshot before each atomic state write; when the primary snapshot is missing, empty, or malformed at startup, the adapter falls back to that last-known-good backup. This is a local recovery aid, not a substitute for managed multi-writer storage.
- Startup reads the newest valid JSON snapshot from the configured primary state/session path or its atomic-write `.tmp` sibling, allowing recovery after an interrupted write while preserving tenant-scoped state boundaries.
- `GET /api/integrations/health` → owner/dispatcher/accountant-only, tenant-scoped communication/payment queue health with webhook-secret checks and stale/failed/pending counts; message totals include `retrying` for transient deliveries waiting on bounded automatic retry, and it reports operational attention separately from process liveness and deployment readiness
- `POST /api/integrations/messages/dispatch` → owner/dispatcher-only bounded dispatch of queued SMS/email messages to the server-side `NORTHSTAR_MESSAGE_PROVIDER_URL`; recipient contact data is resolved from the tenant customer record, each provider request carries the stable Northstar message ID as its idempotency key, asynchronous acknowledgments remain provider-pending, provider responses mark messages `Sent` or `Failed`, and provider credentials never reach the browser. When `NORTHSTAR_MESSAGE_RETRY_LIMIT` is 1–5, transient timeouts and 408/409/425/429/5xx responses are persisted as `Retry scheduled` with bounded 1/5/15/30-minute backoff; permanent failures remain `Failed` for operator action.
- `POST /api/integrations/leads/dispatch` → owner/dispatcher-only bounded dispatch of tenant-owned, provider-undelivered leads to `NORTHSTAR_LEAD_PROVIDER_URL`; the payload preserves contact, service, source, bounded attribution, and receipt context, uses the stable lead ID as the provider idempotency key, records `Delivered`, bounded `Retry scheduled`, or `Failed` state plus provider reference/error and audit evidence, and never exposes provider credentials to the browser
- `POST /api/integrations/inventory/dispatch` → owner/dispatcher/accountant-only bounded dispatch of tenant-owned inventory transactions to `NORTHSTAR_INVENTORY_PROVIDER_URL`; the payload preserves material, location, quantity, source, and job/purchase-order/transfer context, uses the stable transaction ID as the provider idempotency key, records `Delivered`, bounded `Retry scheduled`, or `Failed` state plus provider reference/error and audit evidence, and never exposes provider credentials to the browser
- `POST /api/integrations/accounting/dispatch` → owner/accountant-only bounded dispatch of tenant-owned invoice, settled payment, and purchase-order export records to `NORTHSTAR_ACCOUNTING_PROVIDER_URL`; the payload preserves the canonical accounting-export record, uses a stable record-type/source-ID idempotency key, records `Delivered`, bounded `Retry scheduled`, or `Failed` state plus provider reference/error and audit evidence, and never exposes provider credentials to the browser
- `POST /api/integrations/inventory/retry` and `POST /api/integrations/accounting/retry` → authorized operator recovery actions that reset a failed or retry-scheduled warehouse transaction/accounting record for immediate bounded dispatch, preserve stable provider idempotency, and record an audit event; delivered records cannot be replayed through these controls
- `POST /api/integrations/payments/dispatch` → owner/accountant-only bounded dispatch of provider-pending Card/ACH intents to the server-side `NORTHSTAR_PAYMENT_PROVIDER_URL`; Northstar sends intent metadata including any installment ID and customer contact data but never card or bank credentials, each request uses the stable payment-intent ID as its idempotency key, accepted responses become `Submitted (provider pending)`, failures become retryable `Failed` intents, and settlement still requires the signed payment webhook
- Demo login accepts `role=owner|dispatcher|technician|accountant`; production identity claims must map to the returned permission names and enforce them server-side
- `field:write` is limited to field execution endpoints such as labor/material capture; `jobs:write` remains required for dispatch administration and job creation
- `inventory:read` is limited to owner/dispatcher/accountant reads of materials, stock locations, purchase orders, and inventory transactions; technicians use the assigned-job field endpoints and cannot read internal purchasing or cost records
- Owner logout writes a session revocation record that survives API restarts in development; production should delegate session lifecycle and revocation to the identity provider
- `GET /api/customers` and `POST /api/customers` → list or create tenant-owned customer profiles; creation requires a phone, validates an optional email captured by the owner workspace, rejects duplicate phone/email contacts, accepts an optional `Idempotency-Key` for safe retries, and records a `customer.created` audit event
- `POST /api/customers/import` → owner/dispatcher-only import of up to 500 bounded customer rows (`name`, optional `phone` or `email`, optional `location` and internal `tags`); matches existing contacts by normalized phone/email, reports invalid and duplicate rows without creating them, supports `dryRun: true`, fills only missing existing fields, records one tenant audit event, and accepts an `Idempotency-Key` for safe whole-import retries
- `POST /api/customers/reactivation` → owner/dispatcher-only campaign endpoint that queues deduplicated SMS/email reactivation messages for customers without a recent completed service; only completed jobs establish service recency, while canceled, no-show, and other non-completed records do not suppress eligibility; accepts `inactiveDays` from 30–730 plus an optional normalized internal `tag` filter and returns sanitized queue summaries
- `GET /api/customers/:id` → return one tenant-scoped customer profile with related jobs, assets, estimates, invoices, plans, and activities; each asset includes a bounded `serviceHistory` projection for jobs explicitly linked to that equipment, and `summary` reports completed-service count, latest completed-service timestamp, billed value, collected value, and current open balance from linked records
- `GET /api/customers/:id/timeline?limit=...` → return a bounded, tenant-scoped customer timeline projection of activities, messages, job lifecycle, labor, material-consumption, and inbound request records without requiring consumers to load the full profile payload
- `POST /api/customers/:id/merge` → owner/dispatcher-only, explicit duplicate resolution that reassigns tenant-linked jobs, estimates, invoices, plans, activities, messages, calls, requests, assets, payments, payment intents, financing applications, and locations to the canonical customer; the duplicate is retained with `status: Merged` and `mergedInto` for auditability, contact fields and opt-outs are reconciled safely, and an `Idempotency-Key` makes the operation retry-safe
- Records returned by the owner API enrich legacy name-based customer records with a matching tenant-scoped `customerId` when one can be resolved, preserving compatibility while enabling durable history links
- Owner-facing business records, including derived team and catalog records plus system timeline/audit events, carry an explicit `tenantId` for exports and future managed-storage migration
- Customer profile and timeline joins use an existing `customerId` as authoritative; name matching is only a compatibility fallback for records that have no durable customer link
- The owner portal customer picker passes durable IDs for new notes, assets, and estimates; exact-name ambiguity is rejected in the browser instead of silently selecting the first account
- `PATCH|PUT /api/customers/:id` → update an owner/dispatcher-managed customer's name, phone, email, or primary location with email-shape and duplicate-contact protection plus an actor-attributed `customer.updated` audit event; accepts an optional `Idempotency-Key` and returns `duplicate: true` for a safe retry
- `POST /api/customers/:id/locations` → add a tenant-scoped service address to a customer profile; accepts an optional `Idempotency-Key`, returns `duplicate: true` for safe retries, and appends an actor-attributed `location.created` audit event
- `POST /api/customers/:id/tags` → owner/dispatcher-only replace the customer’s bounded, normalized internal tag set; accepts an `Idempotency-Key`, records an audit event, and never exposes tags through customer tokens
- `POST /api/customers/:id/preferences` → owner/dispatcher-only update of tenant-scoped SMS/email opt-out flags; direct messages, appointment notifications, estimate/invoice reminders, and reactivation campaigns reject or skip opted-out channels, while customer tokens never expose preference metadata
- `GET /api/dashboard?range=week` → `{ metrics, pipeline, tasks, schedule, activity }`
- The owner lead inbox exposes stage, assigned-owner, and source/campaign filters; lead search preserves those filters so operators can work one pipeline slice at a time. The authenticated `GET /api/leads` query accepts bounded `status`, `assignedTo`, and case-insensitive partial `source` filters that match captured source, `utm_source`, `utm_campaign`, or `utm_content`, with tenant-scoped pagination.
- `GET /api/settings/lead-stages` → owner/dispatcher-readable tenant pipeline configuration. `PATCH /api/settings/lead-stages` is owner-only, accepts 2–12 unique non-`Converted` stages, is idempotent when an `Idempotency-Key` is supplied, records an audit event, and refuses to remove a stage still used by an existing lead.
- `GET /api/search` → global operator search also matches lead UTM source, campaign, content, and click IDs and returns the bounded attribution projection with the lead result, preserving tenant isolation and pagination.
- The integration-health workspace exposes bounded message and payment queue dispatch actions for roles authorized by the corresponding provider endpoint; credentials never reach the browser
- `GET /api/reports/overview` → tenant-scoped funnel, scheduling, cash, recurring-revenue, and touchpoint metrics
- `GET /api/reports/custom?metric=...` → owner/dispatcher/accountant-only configurable KPI projection; repeated `metric` parameters select from the tenant's allowlisted report catalog, while omitting metrics returns the first eight defaults; unknown metrics and oversized requests are rejected
- `GET /api/reports/receivables` → owner/dispatcher/accountant-only open-invoice aging with current, 1–30, 31–60, 61–90, and 90+ day buckets, customer-level balances, and invoice-level detail
- `GET /api/export?type=receivables` → owner/dispatcher/accountant-only CSV of open invoice balances with due date, aging bucket, and days-past-due fields
- `GET /api/reports/marketing` → owner/dispatcher/accountant-only source attribution report with lead counts, converted counts, conversion rates, scheduled jobs, attributed lead value, booked revenue, and collected revenue by landing-page source; when UTM campaigns are captured, the response also includes campaign rows with quoted, booked, and collected revenue
- `GET /api/export?type=marketing-campaigns` → owner/dispatcher/accountant-only CSV export of tracked UTM campaigns with source, lead, conversion, conversion-rate, and attributed-value fields
- `GET /api/reports/technicians` → owner/dispatcher/accountant-only technician performance report with jobs, completion/no-show counts, field hours, revenue, material/labor cost, gross margin, and completion rate
- Technician performance also includes a configured commission rate, completed-job commissionable revenue, and payroll-ready commission due; rates default to 10% until changed by an owner
- `GET /api/reports/payroll` → owner/accountant-only payroll-ready report of completed jobs in an optional inclusive `startDate`/`endDate` range (`YYYY-MM-DD`), allocating crew field hours, labor cost, commissionable revenue, and commission due across assigned technicians; `GET /api/export?type=payroll` provides the tenant-scoped CSV handoff
- Report metrics also summarize estimate close rate, memberships sold, no-shows, open customer requests, tracked field hours, material spend, logged labor cost, and gross margin from recorded job data
- `GET /api/export?type=reports` → tenant-scoped CSV of the report metrics for owner and accounting handoff
- `GET /api/team` → tenant-scoped technician roster with derived availability (`Available`, `On job`, or `Unavailable`), active-job counts, non-canceled `timeOffBlocks`, and the next `unavailableUntil` timestamp used for dispatch visibility and assignment validation
- `GET|POST /api/team/:id/time-off` → owner/dispatcher-only tenant-scoped technician unavailability blocks; blocks require a bounded normalized ISO window, reject overlaps and idempotency-key reuse, are returned in chronological order, and participate in assignment/rescheduling conflict checks
- `POST /api/team/:id/time-off/:blockId/cancel` → owner/dispatcher-only recoverable cancellation of a time-off block; preserves the original record and audit note while removing it from future scheduling conflicts, with idempotent replay
- `POST /api/jobs` accepts optional ISO `startsAt`, `endsAt`, and IANA `timeZone` fields; valid timestamp ranges participate in overlap-aware appointment conflict checks
- `POST /api/jobs/:id/reschedule` accepts an available `slotId` or a legacy `time`; slot-based reschedules preserve normalized appointment metadata
- Authenticated technician labor/material writes are limited to the technician's assigned work order; technician roles cannot create inventory or purchase orders
- `POST /api/team` → owner/dispatcher-only creation of a tenant-scoped technician or staff roster member; duplicate names are rejected and an optional `Idempotency-Key` makes browser retries safe
- `GET|POST /api/users` → owner-only tenant-scoped runtime account list/creation for dispatcher, technician, or accountant users; runtime passwords use salted scrypt hashes server-side and are never returned, legacy local HMAC records migrate after successful login, account emails are unique across configured and runtime accounts, and creation accepts an `Idempotency-Key`
- `POST /api/users/:id/status` → owner-only activation or suspension of a runtime account; suspended accounts cannot authenticate, and the current owner cannot suspend their own session
- `POST /api/users/:id/password` → owner-only reset for a runtime account password; passwords use salted scrypt hashes server-side, require at least 10 characters, the reset is audit logged, and previously issued sessions for that account become invalid
- `POST /api/team/:id/commission-rate` → owner-only update of a technician commission rate from 0% through 100%; the rate is tenant-scoped, persisted by technician name, idempotent for same-state retries, and audit logged
- `GET /api/dispatch/recommendations?jobId=...` → owner/dispatcher-only ranking of available technicians by current workload and schedule conflicts; assignment still requires the normal server-side conflict check
- `GET /api/jobs/:id/location-history` → owner/dispatcher or the assigned technician can read a bounded, sanitized location-ping history and live/stale status for the tenant-owned job; customer-facing routes never expose the history
- Dispatch recommendations also include bounded completion/no-show history and use completion performance as a tie-breaker, while skill and schedule conflicts remain hard eligibility rules.
- `GET /api/dispatch/route-manifest?date=YYYY-MM-DD&technician=...` → return a tenant-scoped, normalized-time route ordered by start time with customer, service, address, status, priority, and timezone; technicians are restricted to their own route, while owners and dispatchers may filter by technician
- `GET /api/dispatch/route-calendar?date=YYYY-MM-DD&technician=...` → download the same normalized route as an iCalendar feed for calendar applications; it is tenant-scoped, technician-restricted, excludes canceled/no-show work, and respects saved manual route order.
- `POST /api/dispatch/route-order` → owner/dispatcher-only manual ordering of a technician's complete same-day normalized route; job IDs must be unique and match every active stop for the requested tenant-local date and technician, and retries support idempotency.
- `POST /api/dispatch/route-optimize` → owner/dispatcher-only deterministic coordinate routing for same-day technician stops with verified latitude/longitude coordinates. Northstar seeds a nearest-neighbor route, applies a bounded 2-opt improvement pass, preserves non-overlapping appointment order by default, and returns `distanceKm`, `passes`, and the routing `method`; coordinate-less stops are reported and left unchanged, an optional depot coordinate can seed the route, and retries support idempotency. Set `respectTimeWindows: false` only when dispatch explicitly permits reordering.
- `POST /api/dispatch/bulk-assign` → owner/dispatcher-only atomic assignment of up to 50 non-terminal jobs to one roster technician; validates the complete batch for tenant scope, required skills, technician conflicts across parent and child-visit schedules, and selected-job overlap before mutating any record, clears stale route order, queues confirmations for newly confirmed jobs, records per-job audit/timeline entries, and supports idempotent retries.
- `POST /api/dispatch/bulk-status` → owner/dispatcher-only all-or-nothing lifecycle update for up to 50 jobs (`Confirmed`, `En route`, `In progress`, or `Canceled`); validates every transition and technician requirement before mutation, records per-job audit/timeline events, queues en-route notifications, preserves cancellation notes, and supports idempotent retries.
- Route order metadata is cleared automatically when a job is reassigned or rescheduled, preventing an old route sequence from leaking into a new technician/date.

## Data model starting point

Use `tenantId` on every business record: `customers`, `locations`, `leads`, `jobs`, `estimates`, `payments`, `tasks`, `teamMembers`, and `activityEvents`. Keep `ownerId` and role permissions separate from business records.
